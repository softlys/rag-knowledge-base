# RAG Knowledge Base

Загружаешь PDF или TXT-документы, задаёшь вопросы на естественном языке — сервис находит релевантные фрагменты и формирует ответ на их основе, с указанием источников.

## О проекте

Классическая проблема: у компании есть куча документов (инструкции, договоры, база знаний), и найти в них нужный ответ вручную — долго. RAG (Retrieval-Augmented Generation) решает это так: документ разбивается на куски, каждый превращается в вектор (эмбеддинг), при вопросе система находит самые похожие по смыслу куски и передаёт их модели вместе с вопросом — модель отвечает строго на основе найденного, а не по общим знаниям.

## Возможности

- `POST /upload` — загрузка PDF/TXT, автоматическая нарезка на чанки и индексация
- `POST /ask` — вопрос → ответ, сформированный на основе загруженных документов, с указанием, из какого файла и фрагмента взята информация
- `GET /sources` — список всех загруженных документов в базе
- Локальные эмбеддинги (без API-ключей и лишних сервисов) — используется встроенный движок ChromaDB
- Честный ответ "в базе нет информации по этому вопросу", если релевантных фрагментов не нашлось
- **Демо-режим без API-ключа**: если `ANTHROPIC_API_KEY` не задан (или закончились кредиты), сервис не падает — он честно показывает, что LLM-часть недоступна, но при этом отдаёт реально найденный через векторный поиск релевантный фрагмент. Это позволяет проверить и продемонстрировать работу поиска (самую техническую часть RAG) без каких-либо затрат

## Как это работает

Загрузка: файл → извлечение текста (`pypdf` для PDF) → нарезка на пересекающиеся куски по ~800 символов → сохранение в векторную базу (ChromaDB) с локальными эмбеддингами.

Вопрос: текст вопроса → поиск наиболее похожих по смыслу кусков в базе → формирование промпта с найденным контекстом → запрос к Claude с инструкцией отвечать только на основе присланных фрагментов → ответ + список источников.

## Технологии

- Python 3.12
- FastAPI
- ChromaDB — векторная база данных с открытым исходным кодом
- pypdf — извлечение текста из PDF
- Anthropic Python SDK (Claude API) — генерация ответа
- pytest — тесты с мокнутыми векторной базой и LLM

## Установка

```bash
git clone https://github.com/<your-username>/rag-knowledge-base.git
cd rag-knowledge-base

python -m venv venv
venv\Scripts\activate       # Windows
# source venv/bin/activate  # Linux/macOS

pip install -r requirements.txt

cp .env.example .env
# впиши свой ANTHROPIC_API_KEY в .env
```

## Использование

```bash
uvicorn app.main:app --reload
```
Открой http://localhost:8000/docs

Загрузка документа:
```bash
curl -X POST http://localhost:8000/upload -F "file=@document.pdf"
```

Вопрос:
```bash
curl -X POST http://localhost:8000/ask \
  -H "Content-Type: application/json" \
  -d '{"question": "Какие условия возврата товара?"}'
```

## Тесты

```bash
pytest
```
Тесты не требуют API-ключа и не устанавливают тяжёлые модели эмбеддингов — векторная база и LLM в них мокнуты.

## Технические особенности

- **Локальные эмбеддинги без внешних API**: у Anthropic нет собственного API для эмбеддингов — вместо того чтобы подключать ещё один сторонний сервис, используется встроенный локальный движок ChromaDB. Это упрощает деплой и не требует лишних ключей.
- **Пересекающиеся чанки**: куски текста нарезаются с перекрытием (~120 символов), чтобы не терять контекст на границах разбиения — если важная мысль оказалась на стыке двух кусков, она всё равно попадёт целиком хотя бы в один из них.
- **Явное указание источников в ответе**: каждый ответ сопровождается фрагментами, на основе которых он построен — можно проверить, откуда взята информация, а не просто доверять модели на слово.
- **Промпт с ограничением "отвечай только по контексту"**: снижает вероятность того, что модель придумает ответ из общих знаний вместо реальных данных документа.

## Ограничения

- PDF без текстового слоя (сканы без OCR) не читаются — `pypdf` извлекает только реальный текст.
- Нарезка на чанки — по количеству символов, а не по смысловым границам (абзацам/предложениям) — для более качественного разбиения потребовалась бы дополнительная логика.
- Векторная база локальная (файл на диске) — для продакшена с большим объёмом документов потребовалась бы отдельная выделенная БД.
- Нет разграничения по пользователям/проектам — все документы попадают в одну общую базу.

## Дальнейшее развитие

Идеи на будущее, не реализовано:

- разбиение по смысловым границам (абзацы, заголовки) вместо фиксированного числа символов;
- поддержка .docx и .csv;
- эндпоинт для удаления документа из базы;
- ре-ранжирование найденных фрагментов перед отправкой в LLM для более точного ответа.
